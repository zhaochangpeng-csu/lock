### 03 为什么重新设计门锁

**要点列表（4 项）**

1. **单一识别易被冒用**
   照片、替身和环境噪声都能绕过单一模态，人脸或声纹单独使用都存在明确攻击面。
2. **缺少自然交互**
   传统门锁只有按键与卡片，没有语音、没有对话，用户意图无法被理解。
3. **异常缺少统一记录**
   陌生人徘徊、认证失败不落盘，也没有后续通知与追溯入口。
4. **大模型不宜直接控锁**
   语言模型输出存在不确定性，不能承担开锁这类安全判定职责。

**本页结论**：对话能力增强体验，硬件认证保持安全权威。

---

### 04 四个目标，四条边界

**要点列表（4 项）**

1. **边缘端完成融合认证**
   红外、人脸、活体、声纹四路在 Jetson 本地完成，不依赖云端。
2. **自然语音表达开门意图**
   认证通过后，用户用自然语言说出"开门"即可，无需固定口令。
3. **Agent 只能调用受控工具**
   白名单工具、Bearer Token 鉴权，最终动作仍由 Jetson 本地安全闸门决定。
4. **异常自动落盘形成闭环**
   认证失败自动写入事件文件，为 WorkBuddy / Bot 通知提供入口。

### 06 硬件多模态认证如何工作

**流程 + 参数**

```
红外触发 → InsightFace 人脸识别 → MediaPipe 眨眼/转头活体
        → SpeechBrain ECAPA 声纹（文本无关）→ 人脸/声纹身份一致性
        → 本地加权融合判定
```

**当前融合参数**

| 模块 | 权重 |
|---|---:|
| 人脸 | 0.45 |
| 活体 | 0.25 |
| 声纹 | 0.20 |
| 红外 | 0.10 |

- 融合阈值 **0.78**；默认 `require_all=false`，按加权总分判断
- 声纹阈值 **0.70**，最短有效语音 **2 秒**
- 全部参数集中在 `config.yaml`，可现场调整

**本页结论**：Agent 不参与这些分数的计算，也不能修改融合结果。

### 07 两阶段受控开门

**左图右文**（嵌入 `docs/unlock_sequence.png`）

- **第一阶段：硬件认证**
  融合通过后不立即开锁，Jetson 写入一个 `credential_id`，包含签发时间、`fusion_passed` 与 `consumed` 状态，有效期 **300 秒**，只能消费一次。
- **第二阶段：语音确认**
  用户说"开门"后，FastGPT 必须先调用 `current_auth_context`；仅当凭证可用、新鲜、已授权且未消费时，才调用 `request_unlock(reason)`。
- **本地二次校验**
  Jetson 网关再次检查凭证状态与 `SMART_LOCK_NO_UNLOCK` 后执行动作。
- **兼容原流程**
  `lock.flow=immediate` 可恢复原硬件融合通过后直接执行的模式。

### 08 低延迟语音 Agent 流水线

**流程（5 步）**

| 环节 | 实现 |
|---|---|
| 采集 | 麦克风 → sounddevice / PortAudio，16 kHz 单声道 |
| 流水线 | Pipecat + Silero VAD，管理轮流说话与打断 |
| 识别 | 本地 SenseVoice / FunASR |
| 决策 | FastGPT 工作流 + DeepSeek |
| 合成 | 本地 sherpa-onnx 优先 → ALSA `aplay` 播放 |

**准确口径**：ASR 与 TTS 在本地，DeepSeek 仍需要网络，因此当前**不是完全离线对话**；端到端低延迟数据仍需板端重新测量。Pipecat 只负责流水线生命周期，不参与安全判定。

### 09 四层安全约束

**要点列表（4 项）**

1. **融合层**
   只有 Jetson 本地 `FusionEngine` 能产生认证结果。
2. **凭证层**
   短时、一次性，过期与重复消费均被拒绝。
3. **Agent 层**
   只注册 `current_auth_context` 与 `request_unlock`，不暴露裸 `unlock()`。
4. **执行层**
   Bearer Token、`SMART_LOCK_NO_UNLOCK` 与本地执行器共同控制真实动作。

**本页结论**：即使模型误解或提示词失效，本地安全闸门仍能拒绝无凭证请求。

### 10 安全验证：两个真实场景

**对比表**

| 场景 | 实际工具调用 | 结果 |
|---|---|---|
| 有效凭证 + "请开门" | `current_auth_context` → `request_unlock` | 干运行阻止真实动作 |
| 无效凭证 + "请开门" | 仅 `current_auth_context` | 不调用开锁工具 |

> 两个场景均已完成真实工具调用测试。

### 11 异常事件闭环

**流程 + 数据**

```
认证失败 → localhost:8790/event → 原子写入 latest_event.json
        → SCP 同步到 Windows → WorkBuddy 定时读取 → Bot 通知
        → 成功后标记 processed=true
```

**自动触发条件**

1. 红外持续检测到人员，但超过 **3 秒**仍无法识别人脸
2. 完整认证进入融合阶段后失败（活体 / 声纹 / 身份一致性未通过）

**约束**：同一次人员停留只写一次，离开超过 **5 秒**后重新布防；事件服务异常只记日志并重试，不会改变硬件认证或开锁结果。当前为最小实现，只保留最新一条事件，不是完整消息队列。

### 12 部署、端口与进程治理

**端口分工**

| 服务 | 默认端口 | 部署位置 | 配置入口 |
|---|---:|---|---|
| FastGPT | 3300 | Windows / WSL | `FASTGPT_PORT` / `FASTGPT_API_BASE` |
| 门锁工具网关 | 8787 | Jetson | `LOCK_TOOL_GATEWAY_PORT` |
| 异常事件服务 | 8790 | Jetson 本机 | `LOCK_EVENT_SERVICE_PORT/URL` |

**一键管理**

```bash
./run_smart_lock.sh start | status | restart | stop
```

- 监督 GUI、Pipecat Agent、工具网关、异常服务
- 子进程异常退出后自动拉起
- 停止时清理 PID、临时凭证和 `.tmp` 文件，并释放端口

### 14 关键工程问题与解法

**对比表**

| 问题 | 解决方案 |
|---|---|
| 红外持续为 true 导致重复播报 | 上升沿触发 + 状态保持 + 离开重置 |
| 模型首次使用延迟高 | GUI 与 FunASR 启动时预加载 |
| GUI 声纹和 Agent 同时抢麦克风 | Agent 先等待硬件凭证，认证结束后再开麦 |
| Agent 可能绕过认证 | 一次性凭证 + 本地工具网关，不暴露裸开锁 |
| FastGPT 无法直接访问 Jetson | SSH 本地 / 反向隧道连接 3300 和 8787 |
| 服务异常退出污染端口 | PID 监督、信号清理、强制中断恢复测试 |
| 异常情况没有记录 | 增加独立事件服务和单文件原子写入 |
| Jetson 音频路径不统一 | 输入统一 PortAudio，输出统一 ALSA `aplay` |

### 15 当前边界与风险

**要点列表（6 项）**

1. **开发板 SSH 中断** — 当前在密钥交换阶段主动关闭连接，最新改动尚未同步
2. **执行器为串口风扇模拟** — 真实继电器需有人看护并保持可断电状态测试
3. **DeepSeek 仍依赖网络** — 断网时硬件认证可运行，但 `agent_confirm` 对话开门不可用
4. **稳定性数据缺失** — 回声消除、长时间打断稳定性与端到端延迟尚无正式数据
5. **事件存储为最小实现** — `latest_event.json` 只保留最新一条，生产版应升级为 SQLite 或消息队列
6. **Nano 4GB 资源余量未知** — 需更小 ASR 或模型量化方案才能宣称支持

**汇报原则**：这些是下一阶段工程工作，不影响已完成的架构验证结论。
